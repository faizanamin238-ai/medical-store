# Medical Store SaaS

Multi-tenant pharmacy management software. Each pharmacy is one tenant, isolated by Postgres Row-Level Security.

Feature surface today: medicine catalog, point of sale, sales history & receipts, suppliers & purchases, customers & prescriptions, reports (sales, top medicines, profit margin, stock alerts), team management with roles/invites, audit log at `/activity`, and per-tenant settings (currency, timezone, tax, logo, receipt footer).

---

## Stack

- **Next.js 15** (App Router, React Server Components, Server Actions, Turbopack)
- **TypeScript** (strict mode)
- **Supabase** — Postgres + Auth + Storage + Realtime
- **Tailwind CSS v4** + shadcn/ui (Base UI under the hood)
- **react-hook-form** + **zod** for validation
- **TanStack Table** for grids · **Recharts** for charts
- **Playwright** for end-to-end tests
- Hosted on **Vercel**

Package manager: npm.

## Getting started

### 1. Clone & install

```bash
git clone git@github.com:faizanamin238-ai/medical-store.git
cd medical-store
npm install
```

### 2. Configure environment

Create `.env.local` at the project root:

```ini
NEXT_PUBLIC_SUPABASE_URL=https://<project>.supabase.co
NEXT_PUBLIC_SUPABASE_ANON_KEY=<anon-public-key>
SUPABASE_SERVICE_ROLE_KEY=<service-role-key>   # server-only — never expose to the client

# Optional — enables a "Demo Mode" toggle on /login that signs visitors
# in as a shared demo account. Both must be set together. Leave both
# unset in production to hide the affordance.
DEMO_USER_EMAIL=demo@example.com
DEMO_USER_PASSWORD=<demo-password>
```

`.env.local` is git-ignored; do not commit it.

### 3. Apply migrations & seed (first time only)

The repo ships with timestamped SQL migrations under `supabase/migrations/` and a `supabase/seed.sql` with sample data for the demo pharmacy.

```bash
# Push migrations
npx supabase db push --linked

# Load demo data
npx supabase db query --linked --file supabase/seed.sql
```

### 4. Run the dev server

```bash
npm run dev
```

The app boots at <http://localhost:3000>. Sign up creates a new pharmacy tenant; the **Demo Mode** tab on `/login` signs you straight in as the configured demo user when the env vars above are set.

## Architecture notes

### Multi-tenant isolation

Tenancy is enforced in the database, not the UI. Every tenant-scoped table has Row-Level Security enabled with policies that reference `pharmacy_id = public.get_user_pharmacy_id()`. The Server Component / Action layer trusts RLS — UI role-gating is purely cosmetic on top.

### Mutations always go through Server Actions

Files in `lib/actions/` are the only place that write to Supabase. Each action:

1. Parses input with a zod schema from `lib/validators/`.
2. Calls Supabase using the request-scoped server client.
3. Calls `revalidatePath` for any view that needs to update.
4. Returns a typed `{ data?, error? }` result.

Client components never import the Supabase client to mutate data.

### Atomic, transactional stock changes

Sales and purchases (which write a parent row + items + adjust stock) use Postgres RPCs marked `SECURITY DEFINER` — `checkout_sale()` and `create_purchase_with_items()` — so all three writes succeed or all three fail.

### Audit log

The `audit_row_change` trigger writes to `audit_logs` on every INSERT / UPDATE / DELETE for medicines, sales, purchases, customers, suppliers, and profiles. UPDATEs are stored as `{ field: { old, new } }` so the UI at `/activity` renders a proper before → after diff. Server Actions that don't go through a trigger (settings, invites, exports) call `logAudit()` from `lib/audit.ts`.

### Per-tenant currency / timezone / tax

Read from the `pharmacies` row. Never hardcode `PKR`, `Asia/Karachi`, or any specific tax rate — settings are surfaced in `/settings` and used everywhere downstream.

## Testing

Playwright e2e tests live in `e2e/`, one file per module. The webServer config boots its own dev server.

```bash
# Run everything
npm run test:e2e

# Single file
npx playwright test e2e/auth.spec.ts

# UI mode (best for debugging flaky locators)
npm run test:e2e:ui
```

Tests that need a logged-in session use the Demo Mode flow — set `DEMO_USER_EMAIL` and `DEMO_USER_PASSWORD` in your shell or `.env.local` before running.

## Deployment

- **Platform:** Vercel (project linked to the `main` branch).
- **Auto-deploy:** every push to `main` triggers a production deploy.
- **Auto-push:** `.git/hooks/post-commit` pushes to `origin` after every local commit so the deploy follows the commit automatically.
- **Env vars (production):** `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_ANON_KEY`, `SUPABASE_SERVICE_ROLE_KEY`. Leave the `DEMO_USER_*` vars unset in production unless you want the demo affordance visible there too.
