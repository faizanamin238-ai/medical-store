# CLAUDE.md — Medical Store SaaS

Multi-tenant pharmacy management SaaS. Each pharmacy = one tenant, isolated by Postgres Row-Level Security.

Full product spec lives in [medical-store-saas-plan.md](medical-store-saas-plan.md). This file is the working rails for code.

---

## Stack

- **Next.js 15** (App Router, React Server Components, Server Actions)
- **TypeScript** (strict mode on)
- **Supabase**: Postgres + Auth + Storage + Realtime
- **Tailwind CSS** + **shadcn/ui** (copy-paste components in `components/ui/`)
- **react-hook-form** + **zod** for forms and validation
- **TanStack Table** for data grids
- **Recharts** for reports
- **react-pdf** / **pdfme** for receipts and invoices
- **Vercel** for hosting

Package manager: npm.

## Non-negotiable rules

1. **RLS is the security boundary, not the UI.** Every tenant-scoped table must have RLS enabled and policies that reference `pharmacy_id = public.get_user_pharmacy_id()`. UI role-gating is a UX nicety on top.
2. **Never expose `SUPABASE_SERVICE_ROLE_KEY` to the client.** It bypasses RLS. Server-side only, and only when absolutely required.
3. **All mutations go through Server Actions** in `lib/actions/`. No client-side direct writes to Supabase for CRUD.
4. **Validate every input with zod on the server**, even if the client already validated. Zod schemas live in `lib/validators/`.
5. **Currency, timezone, tax are per-tenant.** Read from the `pharmacies` row. Never hardcode `PKR`, `Asia/Karachi`, or a specific GST rate.
6. **Stock mutations must be transactional.** A sale that decrements stock + inserts `sales` + inserts `sale_items` is one atomic Postgres transaction (use an RPC / `pg` function if Server Action can't express it cleanly).

## Project structure

```
app/
  (auth)/          login, signup, reset-password — public
  (dashboard)/     everything behind auth; layout enforces session
  api/             webhooks, CSV import endpoints
components/
  ui/              shadcn/ui — generated, don't restyle ad hoc
  <feature>/       feature-specific components (medicines/, pos/, ...)
lib/
  supabase/        client.ts (browser), server.ts (RSC/Actions), middleware.ts
  actions/         Server Actions — one file per resource
  validators/      zod schemas — one file per resource
  utils.ts
types/
  database.types.ts   generated by `supabase gen types`
supabase/
  migrations/      SQL migrations, one timestamped file per change
  seed.sql
```

One module = one folder under `app/(dashboard)/<module>/` + one file in `lib/actions/<module>.ts` + one file in `lib/validators/<module>.ts` + components in `components/<module>/`.

## Naming conventions

- **Database:** `snake_case` for tables and columns. Tables are plural (`medicines`, `sales`).
- **TypeScript:** `camelCase` for variables and functions, `PascalCase` for types and components.
- **Files:** `kebab-case.tsx` for components and pages, `camelCase.ts` for utilities, action files match the resource (`medicines.ts`).
- **Server Actions:** verb-first (`createMedicine`, `updateMedicine`, `deleteMedicine`, `listMedicines`).
- **Zod schemas:** `<Resource>Schema` (e.g. `MedicineSchema`, `CreateMedicineInput`).

## Standard CRUD module pattern

For every resource (medicines, suppliers, customers, ...):

1. **Migration** — table + indexes + `alter table ... enable row level security` + 4 policies (select / insert / update / delete).
2. **Type regen** — `npx supabase gen types typescript --project-id <id> > types/database.types.ts`.
3. **Validator** — zod schema in `lib/validators/<resource>.ts` (one for create, one for update if shapes differ).
4. **Actions** — Server Actions in `lib/actions/<resource>.ts`. Each action: parse with zod → call Supabase → `revalidatePath` → return typed result.
5. **Pages** — list (`page.tsx`), create (`new/page.tsx`), edit (`[id]/page.tsx`) under `app/(dashboard)/<resource>/`.
6. **Components** — form, table, filters in `components/<resource>/`.

## RLS policy template

Apply to every tenant-scoped table:

```sql
alter table <table> enable row level security;

create policy "<table>_select_own_pharmacy"
  on <table> for select
  using (pharmacy_id = public.get_user_pharmacy_id());

create policy "<table>_insert_own_pharmacy"
  on <table> for insert
  with check (pharmacy_id = public.get_user_pharmacy_id());

create policy "<table>_update_own_pharmacy"
  on <table> for update
  using (pharmacy_id = public.get_user_pharmacy_id())
  with check (pharmacy_id = public.get_user_pharmacy_id());

create policy "<table>_delete_managers_only"
  on <table> for delete
  using (
    pharmacy_id = public.get_user_pharmacy_id()
    and exists (select 1 from profiles where id = auth.uid() and role in ('owner','manager'))
  );
```

Adjust the delete policy per the role matrix in section 7 of the plan.

## Roles

Four roles on `profiles.role`: `owner`, `manager`, `pharmacist`, `cashier`. Permission matrix lives in the plan (section 7). Encode role checks in RLS first; mirror them in the UI for clarity.

## How to work with me (Claude)

- Build **one module end-to-end** before starting the next. Migration → RLS → types → validators → actions → pages → components.
- **Implement step by step.** Break every feature into small, discrete steps. Complete and confirm each step before moving to the next — never jump ahead or batch unrelated changes together.
- **Test run until correct.** After implementing any step, run the dev server (or relevant test) and verify the feature works end-to-end. Do not mark a step done until it passes. If it fails, fix it before proceeding.
- **Playwright for functional testing.** Every feature must have a Playwright e2e test covering the happy path and key edge cases. Run `npx playwright test` after implementation — all tests must pass before a feature is considered done. Tests live in `e2e/` at the project root.
- When I write code that mutates the DB schema, ask the user to run `supabase gen types` before continuing so I have fresh types.
- Don't ask "should I add tests?" for trivial UI — do ask, and write them, for: sale checkout (stock decrement, atomicity), RLS tenant isolation, CSV import edge cases.
- Read every file I create before committing.
- Commit working code before starting the next change. One feature = one branch = one PR.
- **Commit and push on phase completion.** When a phase is fully done and all tests pass, commit all changes with a clear phase-scoped message and push to `origin main`.
- For UI work: run the dev server and click through the feature before reporting done.
